## 1. Idempotent Setpoint Handling (`already_set`)

Upstream `yoziru/tesla-ble` v5.2.0 (`src/vehicle.cpp:985-988`) treats CarServer `already_set` responses as success (`actionStatus.result == OK`) rather than throwing an action failure.

### Test Case 1a: `set_charge_limit` with Existing Limit (100%)
With the vehicle already configured at 100% charge limit, `POST /api/1/vehicles/<VIN>/command/set_charge_limit` was invoked with `{"percent":100}`:

**HTTP Response:**
```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 124

{"response":{"result":true,"command":"set_charge_limit","vin":"<redacted>","reason":"command executed successfully"}}
```

**ESP32 Ring-Buffer Log:**
```text
I (1336626) vehicle_ctrl: VCSEC sleep flag: AWAKE
  ActionStatus:
    result: ERROR
  ResultReason:
    which_reason: 1
    plain_text: already_set
[Set Charge Limit] Command completed successfully in 5154 ms
```
*Result*: The vehicle returned `ActionStatus: result: ERROR, plain_text: already_set`. Upstream v5.2.0 mapped this to successful command completion.

## 2. Request-UUID Matching Gate (Command Directly Following Session Refresh)

In `yoziru/tesla-ble` v5.2.0 (`src/vehicle.cpp:931-941`), CarServer responses carrying a non-empty `request_uuid` are validated against `last_request_uuid_` for `DOMAIN_INFOTAINMENT`. Stale responses from prior requests or aborted queries are dropped instead of falsely completing whichever request currently heads the FIFO.

### Test Case: Rapid Command Dispatch Around Session Refresh
An Infotainment session refresh occurred immediately prior to command and telemetry dispatches. In-flight CarServer responses from prior operations arrived after the session update and counter bump:

```text
Updating counter to 4716 (old_counter=0)
Session updated for DOMAIN_INFOTAINMENT
[VCSEC Health Poll] Command completed successfully in 272 ms
[Charge State Poll] Command completed successfully in 1147 ms
I (133777) http_server: REQ: POST /api/1/vehicles/<VIN>/command/set_charging_amps
...
Ignoring CarServer response for a different request
...
Ignoring CarServer response for a different request
```

**Syslog Collector Verification:**
Multiple occurrences of `Ignoring CarServer response for a different request` were recorded in the syslog sink during burst command readbacks (`Verify Charging Amps`) following the session refresh.

*Result*: The Request-UUID gate successfully detected and dropped mismatched responses, preventing out-of-order completions and maintaining FIFO integrity across session boundaries.

## 3. BLE RX Framing Recovery under Weak Link Conditions (-83 to -94 dBm)

During command and telemetry polling under weak BLE link conditions (`rssi: -90` to `-94 dBm`), corrupted RX frames occurred and were handled by the rebased Patch 0003 recovery mechanism:

### Test Case 3a: Recovery during `wake_up`
```text
I (116547) http_server: REQ: POST /api/1/vehicles/<VIN>/command/wake_up
I (116547) http_server: CMD wake_up on VIN <VIN>
RX framing recovery: invalid message length; attempting recovery; suppressed 0 similar events
I (120537) vehicle_ctrl: HEAP free=104340 largest_block=53248 min_free=83012 internal_largest=53248
[Wake] Command completed successfully in 4564 ms
```

### Test Case 3b: Candidate Scanning during Readback Verification
```text
RX framing recovery: invalid message length; attempting recovery; suppressed 0 similar events
[parse_universal_message] Decoding failed: invalid wire_type
[parse_universal_message] Decoding failed: wrong wire type
...
[Verify Charging Amps] Command completed successfully in 4587 ms
I (249836) vehicle_ctrl: set charging amps verified: requested=6 A applied=6 A request=6 A actual=0 A
```

*Observations & Scope*:
1. Patch 0003's `log_rx_recovery_()` logged the framing violation (`invalid message length; attempting recovery; suppressed 0 similar events`) through the rate-limited channel.
2. `attempt_buffer_recovery_()` retained the buffer, scanned candidate offsets, and successfully parsed the remaining valid protobuf payload without dropping the BLE connection or faulting the command queue.
3. *Trace Scope Note*: The live trace demonstrates that candidate offset scanning successfully recovers valid framing and allows in-flight commands (`wake_up`, `set_charging_amps`) to complete without tearing down the BLE link. The 1-hour log suppression roll-over was not exercised in this single-event trace.

- **Continuous Uptime**: >29,700 seconds (>8.2 hours) without reboot or fault.
- **Sleep Preservation**: Vehicle remained asleep continuously (`vcsec_sleep: ASLEEP`, `link: asleep`) with 0 wake-ups or battery drain events.
